# 测试结果与方法

> 🌐 **中文** | [English](Benchmarks.en.md)

## 1. 测试环境

| 项目 | 值 |
|------|----|
| CPU | Intel Core i5-10400（Comet Lake，6 核 12 线程，2.90 GHz，无 AVX-512 / VNNI） |
| 内存 | 8 GB，**单通道** DDR4（SPD 3200，实际 2666 MT/s） |
| 系统 | Windows 10 22H2（build 19045） |
| 编译器 | MSVC 14.51（VS2026）+ Clang 20.1.8（LLVM） |
| 模型 | `Bonsai-8B.gguf`（Qwen3-8B，全 Q1_0，1.07 GiB） |
| 线程 | 6（物理核数） |
| 轮次 | `-r 3`（每项 3 次取均值 ± 标准差） |

> 本机使用 `haswell` 变体（AVX2，无 VNNI）。VNNI 路径无法在本机运行，
> 但已通过反汇编验证指令生成。

> ⚠️ **测试机为单通道内存**（8 GB DDR4-2666，实测流式读带宽约 14–17 GB/s）。
> **tg 是内存带宽瓶颈**，因此本文所有 tg 绝对值都被单通道上限压制（理论 ~15.7 tok/s）；
> pp 为计算受限，受影响较小。跨平台比较时请重点关注同场 A/B 的**提升比例**，而非本机绝对值。
> （本机同时运行其它应用，A/B 测量也可能受影响。）

## 2. 主结果：分块路径 vs 通用路径

`Lumina-Engine-bench.exe -m Bonsai-8B.gguf -p 32,64,128,256,512 -n 32,64,128 -t 6 -r 3`

**通用路径**（`GGML_NO_Q1_TILE=1`，仍含 `vpsignb` + VNNI）：

| 测试 | t/s |
|------|----:|
| pp32  | 13.18 ± 0.29 |
| pp64  | 13.14 ± 0.35 |
| pp128 | 13.11 ± 0.18 |
| pp256 | 12.98 ± 0.06 |
| pp512 | 12.83 ± 0.05 |
| tg32  | 9.60 ± 0.17 |
| tg64  | 9.58 ± 0.09 |
| tg128 | 9.53 ± 0.09 |

**优化后**（Q8_128 分块路径）：

| 测试 | t/s | 相对通用 |
|------|----:|--------:|
| pp32  | **18.78 ± 0.55** | **+42.5%** |
| pp64  | **18.46 ± 0.44** | **+40.5%** |
| pp128 | **17.94 ± 0.40** | **+36.8%** |
| pp256 | **17.31 ± 0.27** | **+33.4%** |
| pp512 | **16.49 ± 0.18** | **+28.5%** |
| tg32  | **10.68 ± 0.55** | **+11%** |
| tg64  | **11.01 ± 0.42** | **+15%** |
| tg128 | **10.19 ± 0.25** | **+7%** |

> tg 使用独立的单列 GEMV 路径（见 §2.1）。上表为 6 线程值，机器状态影响较大；
> 可靠对比请用同场交替 A/B。

### 2.1 Token 生成（tg）同场交替 A/B

新旧 CPU 后端 DLL 交替运行（`-p 64 -n 32,64,128 -t 12 -r 3`，两轮均值）：

| 测试 | 旧版 | **新版** | 提升 |
|------|-----:|---------:|-----:|
| tg32  | 11.27 | **12.67** | **+12.4%** |
| tg64  | 11.22 | **12.83** | **+14.3%** |
| tg128 | 11.17 | **12.69** | **+13.6%** |

6 线程约 +4–10%（更接近单通道带宽上限）。行分组大小可用 `GGML_Q1_GEMV_ROWS=1\|2\|4` 微调。

### 受控 A/B（同场交替 3 轮，排除机器状态漂移）

`Lumina-Engine-bench -p 32,128,512 -n 1 -t 6 -r 2`

| 轮次 | pp32 通用 → 分块 | pp128 通用 → 分块 | pp512 通用 → 分块 |
|------|------------------|-------------------|-------------------|
| 1 | 13.46 → 16.57 | 13.08 → 16.28 | 12.74 → 16.09 |
| 2 | 13.23 → 16.43 | 13.05 → 16.21 | 12.79 → 16.10 |
| 3 | 13.15 → 16.81 | 12.85 → 16.51 | 12.72 → 16.09 |
| **均值提升** | **+25%** | **+26%** | **+26%** |

## 5. 独立内核微基准

`bench_kern.cpp`（单线程，8 次取均值，热数据）：

| 内核 | GMAC/s |
|------|-------:|
| 原 `xor+sub` | 16.76 |
| **`vpsignb`（现行）** | **18.53** (+10.6%) |
| `vpsignb` + unroll2 | 18.23 |
| `vpsignb` + prefetch | 17.6（无益） |

`bench_tile.cpp`（单线程，MSVC `-O2 -arch:AVX2`）：

| 内核 | GMAC/s |
|------|-------:|
| 通用（未分块） | 17.1 |
| 分块 2×4 | 27.6 |
| 分块 4×2 | 26.2 |
| 分块 2×8 | 29.9 |
| 分块 4×4 | **30.8** |

> 分块内核在独立微基准中比通用内核快 ~1.8×；在完整模型中由于框架本身已有
> 16×16 分块，净收益约 +25%。

### 内存带宽探针

`bench_mem2.cpp`（向量化读，1 GB 数组）：

| 线程 | 读带宽 |
|-----:|-------:|
| 1 | 14.1 GB/s |
| 6 | 16.7 GB/s |
| 12 | 16.1 GB/s |

复制带宽约 4.3–4.8 GB/s。这解释了 tg 的上限：`1.06 GB / 16.7 GB/s ≈ 63 ms`
→ 理论 ~15.7 tok/s，实际 ~9.5（其余为其它算子与同步开销）。

## 6. 困惑度

`Lumina-Engine-perplexity.exe -m Bonsai-8B.gguf -f docx/whitepaper.txt -c 512 -t 6 --chunks 4`

| 配置 | PPL |
|------|----:|
| 通用路径（Q8_0 激活） | 5.7160 ± 0.507 |

## 7. 机器噪声说明

本机为办公机，绝对性能会随温度/负载漂移（同一配置不同时段 pp512 可在 13.0–16.5 之间）。
因此：

- **只信同场交替 A/B 的比值**，不要跨时段比较绝对值。
- 微基准比 `Lumina-Engine-bench` 更稳定，但仍有 ~10% 波动。
- 所有结论均基于同场交替测量。

## 8. 二值查表（Q1LUT，默认启用）

> 9-23 复核推翻了本节早前的“无收益”结论：那是机器降频/后台负载下的假象。以下为受控交替 A/B。

tg（`-p 64 -n 128 -t 6 -r 3`，off/lut 交替）：

| 配置 | 打包 GEMV (t/s) | Q1LUT (t/s) |
|---|---:|---:|
| 本机（AVX2 无 VNNI） | 9.70 / 9.99 | **13.04 / 13.01（+30%）** |

pp（受控 A/B：`GGML_Q1_LUT=0` vs 默认）：

| 测试 | 分块 GEMM (t/s) | Q1LUT pp (t/s) | 变化 |
|---|---:|---:|---:|
| pp8 | 16.9 ~ 18.3 | 20.8 ~ 23.7 | ~ +27% |
| pp64 | ~ 17.0 | ~ 21.4 | +26% |
| pp512 | ~ 15.8 | ~ 19.9 | +26% |
| pp1024 | 19.68 | 24.82 | +26% |
| pp2048 | 14.58 | 22.86 | +57% |

K 分块对照（`GGML_Q1_LUT_KB`，`-p 64 -n 128 -t 6`）：

| KB | tg128 (t/s) |
|---:|---:|
| 0（整表，默认） | ~12.0 |
| 1024 | ~11.0 |
| 2048 | ~11.1 |
| 4096 | ~11.9 |

单线程内核微基准（`bench/bench_lut2.cpp`，K=4096，M=65536，正确性 max err ~1e-8）：

| 内核 | GMAC/s |
|---|---:|
| 现有符号 GEMV（Q8_128） | 25.9 |
| **二值激活查表 GEMV（32 行）** | **46.2 (+78%)** |

数值正确性：PPL 同量级（LUT 5.7049 vs 关闭 5.7173，差异来自浮点求和顺序），长提示贪婪输出逐字一致。

结论：tg 与 pp（`ne11>=8`）默认走 Q1LUT，pp（`2..7`）走分块 GEMM；`GGML_Q1_LUT=0` 可整体关闭
（额外约 0.95 GiB 内存，首次使用约 0.7 s 置换开销）。

## 9. 复现命令

```bat
cd C:\Lumina-Engine\Lumina-Engine-Bin

REM 二值查表 A/B（默认开启；关闭用 GGML_Q1_LUT=0）
set GGML_Q1_LUT=0
Lumina-Engine-bench.exe -m ..\Bonsai-8B.gguf -p 64 -n 128 -t 6 -r 3
set GGML_Q1_LUT=
Lumina-Engine-bench.exe -m ..\Bonsai-8B.gguf -p 64 -n 128 -t 6 -r 3

REM 主结果
Lumina-Engine-bench.exe -m ..\Bonsai-8B.gguf -p 32,64,128,256,512 -n 32,64,128 -t 6 -r 3

REM 通用路径对照
set GGML_NO_Q1_TILE=1
Lumina-Engine-bench.exe -m ..\Bonsai-8B.gguf -p 32,64,128,256,512 -n 32,64,128 -t 6 -r 3
set GGML_NO_Q1_TILE=

REM tg 单列 GEMV 对照（新旧 DLL 同场交替）
set GGML_NO_Q1_GEMV=1
Lumina-Engine-bench.exe -m ..\Bonsai-8B.gguf -p 64 -n 32,64,128 -t 12 -r 3
set GGML_NO_Q1_GEMV=
Lumina-Engine-bench.exe -m ..\Bonsai-8B.gguf -p 64 -n 32,64,128 -t 12 -r 3

REM tg 行分组扫描
for %R in (1 2 4) do set GGML_Q1_GEMV_ROWS=%R && Lumina-Engine-bench.exe -m ..\Bonsai-8B.gguf -p 64 -n 128 -t 12 -r 3
set GGML_Q1_GEMV_ROWS=

REM 困惑度
Lumina-Engine-perplexity.exe -m ..\Bonsai-8B.gguf -f ..\docx\whitepaper.txt -c 512 -t 6 --chunks 4
```
